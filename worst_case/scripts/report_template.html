Shellsort · worst-case comparisons · N = 6 … 512

Worst-case-optimal Shellsort gap sequences

An independent derivation of the gap sequences that minimise the worst-case number of comparisons, with every optimum for N ≤ {{N_LAST}} proved exactly and every larger-N figure backed by a concrete input that attains it.

Findings

  • Replication. For {{N_MATCH}} of {{N_TOTAL}} sizes in N = 6 … {{N_LAST_README}} the optimal worst case equals the reference table, found from scratch by an exhaustive search over all gap sets.

  • Proof instead of belief. Each optimum is certified by an exact dynamic program over threshold sets (up to 2.5·1010 states), so the reference values that were only believed exact are now proved, and every rejected sequence carries an input that makes it worse.
  • Tie lists. The search returns all optimal sequences. It finds ties the reference missed and one listed tie that is not optimal ({1,3,7,12} at N = 14 costs 67, not 64).
  • Better choice at N = 22. {1,3,5} reaches the same worst case (131) as {1,4,7,9} with a lower exact average (94.51 vs 97.47).
  • Large N. {{LARGE_FINDING}} The independent search rediscovers the README's sequences at N = 91 and 128. Calibrated equal-budget races (below) leave the README sequence as the only contender not pushed to the next level at N = 91, 128, 181 and 256. At N = 362 the races leave it tied, and N = 64 cannot be ranked at the measurable level. No sequence is shown to beat it at any N ≥ 64. Family screens of about 428,000 complete sequences at N = 64 … 512 found no core that competes with {1,4,9,11}, and fixed-budget attacks of up to 4G moves per thread (8–15G in total for each leader) keep the README sequence the sole leader at N = 91 (≥ 1045), 128 (≥ 1661) and 181 (≥ 2646, every rival ≥ 2652). At N = 256 and 362 they push the README sequence to ≥ 4193 and ≥ 6576, while new sequences from the screens stay lower, led by {1,4,9,11,30,47,67,95} (≥ 4171) and {1,4,9,11,30,36,70,109,171} (≥ 6521), each after about 7.5G moves per thread. At N = 512, beyond the README table, a screen of 15,990 sequences and rounds of up to 4G moves per thread leave {1,4,9,11,30,36,59,98,162,213} with the lowest bound (≥ 10119 after 8.6G moves per thread), ahead of {1,4,9,11,30,36,70,109,195,248} (≥ 10150 after 3.6G). These are lower bounds, so this ranks the sequences at that effort but does not prove one better.

Why these sequences win

Before pass h, the array is already d-sorted for every distance d that is a sum of earlier gaps. A pass costs at least N − h comparisons plus one per inversion its chains still contain, so each gap is worth what it removes from the later passes, minus its own fixed price. Three regimes appear.

  • N ≤ 15: two or three passes with large gaps near N; many ties.
  • 16 ≤ N ≤ 37: the core {1,4,7,9}, optimal at 19 of these 22 sizes. After the 9-, 7- and 4-passes only six distances {1,2,3,5,6,10} can still be inverted, so insertion sort finishes with about three comparisons per element. A single gap h ≥ N/2 is added when its fixed cost N − h is smaller than what it saves.
  • 38 ≤ N ≤ 42: a transition in which both cores appear among the optima.
  • 43 ≤ N ≤ 45: the core {1,4,9,11} with 21. The {4,7,9} core keeps the last pass cheaper, but its decoupled 9-pass grows too expensive; the bare {4,9,11} core overtakes it at N ≈ 40.

Large N: lower bounds only

Exact search is impossible here, so every value is a lower bound attained by an explicit, re-simulated input. The independent search (seeded only from this work's own optima) rediscovers the README's sequences at N = 91 and 128. Candidates from this work and from the README author's earlier searches were then compared in equal-budget races: each contender gets the same targeted-search budget to reach a given value; reaching it shows the contender is at least that bad.

    {{RACE_VERDICTS}}

Ranking sequences by lower bounds favours sequences whose worst inputs are merely hard to find. At N = 64 two early apparent winners, {1,4,9,11,32,62} and {1,4,9,11,32,63}, were later shown to reach 631 by the README author's hill-climber, which is why the verdicts rely on equal-budget races rather than single runs.

Restart length and calibration. Which restart length finds a sequence's worst inputs depends on the sequence. At N = 64, 144 long annealing runs never pushed {1,4,9,11,21,60} or {1,4,9,11,21,62} above 630, but 4M-move restarts reached 631 in 21 s and 2 s; {1,4,9,11,21,57} behaved the other way round. The later races therefore use Luby restarts, which mix every run length, and each one is calibrated: it includes a contender already known to reach the target, attacked afresh. If the budget misses that known value, the survivals in the race mean nothing. This removed two earlier verdicts: the README sequence's sole lead at N = 91 (it reaches 1045 too) and its 10-comparison lead at N = 256 (it reaches 4152 too).

Family screens and fixed-budget attacks (N = 64 … 512)

Family screens scored complete sequences from hundreds of 4-gap cores ({1,4,9,c}, {1,4,7,9}, {1,4,10,c}, {1,3,b,d}, {1,5,b,d}, …) by successive halving with short annealing runs, then refined around the finalists. No core competes with {1,4,9,11}. Only {1,4,9,15} stays close: its best member is 18 behind at N = 128, 7 at N = 181, 23 at N = 256, 31 at N = 362 and 113 at N = 512 in the first attack round, while {1,4,7,9} and the other cores fall 25–34 behind at N = 128. The best candidates then got the same number of moves each with no target, so their bounds are comparable. Parallel tempering, a replica-exchange annealer, did best at N = 64; from N = 128 on, Luby restarts with long base runs did better, and at N = 362 a single anneal of the whole budget per thread did best. Worst case of the average-optimal sequences

The README also lists, for each N, the sequence with the lowest average and that sequence's worst case. N = 46 is not in the README table; its average-optimal sequence {1,4,13,41} was supplied by the README author. At N = 512 the README names {1,4,10,23,57,189,484} as the best average, without a worst case; its author has since found with more samples that {1,4,10,23,57,189,483} is slightly better, and that sequence is used here. The worst cases were checked here: exactly by the same dynamic program wherever it fits in 12 GB (every N ≤ 46), and otherwise by annealing searches for worse inputs, which only give lower bounds. For N ≥ 64 each of these sequences got as many annealing moves as the best worst-case sequence of its size, so the two bounds rest on the same effort. Every value is attained by a stored input that is re-simulated.

Method

  1. Exact worst case of one sequence. Inputs are viewed as chains of threshold sets; sorting commutes with thresholding, so the comparisons become edge weights of a lattice and the worst case is a longest path. The first pass is decoupled exactly, passes with gap ≥ N/2 are absorbed as compare-exchange constraints (or, when every pair links the head of one chain of the next gap to the tail of another, turned into edge penalties on the smaller state space without them), free positions are back-filled (an exchange argument shows this loses nothing), and very large instances run level by level in about 10 GB.
  2. Bad inputs at any size. Annealing with incremental evaluation (a swap of values x < y only changes the threshold sets between them), polished by an exact dynamic program that re-orders a window of consecutive values.
  3. Sequence search with continuous pruning. A branch-and-bound over gap prefixes. An input that is untouched by every larger gap is a valid lower bound for the whole family of extensions, so one input prunes an entire subtree; killer inputs are pooled and reused, and the threshold only falls when a value is proved exactly.
  4. Holistic candidates. Candidates are always complete sequences generated family by family; no step perturbs a single gap. At large N the top gaps are re-chosen jointly on top of the best prefixes from the previous size.
  5. Parallel by construction. Subtrees, candidate batches and DP levels are independent units of work (OpenMP on 24 threads here; the same units could be spread over machines).
